# ROS 2 핵심 개념

통신 방식부터 Nav2 · ros2_control 생태계까지 훑으면서 정리한 노트.
각 개념을 이미 알고 있던 것에 붙여서 이해한 기록이라 비유가 섞여 있다.

---

## 통신 3형제

| 개념 | 설명 | 이해에 쓴 비유 |
|---|---|---|
| Topic | 발행자가 채널에 데이터를 계속 흘려보내고 구독자가 받는 단방향 통신. 응답이 없고, 구독자가 몇 명이든 발행자는 신경 쓰지 않는다 | 학습 중 reward/observation을 로그로 계속 흘려보내는 것과 같은 방송 구조 |
| Service | 요청 하나에 응답 하나가 오는 통신. 다만 ROS 2에서는 호출이 기본적으로 비동기(call_async)이고, 응답은 콜백이나 future로 받는다 | 함수 호출과 비슷하지만, 결과를 기다리는 방식이 다르다 |
| Action | 목표 전달 → 진행 상황 피드백 → 최종 결과. 중간 취소가 가능하다. 별도의 통신 방식이 아니라 Service 3개(goal/result/cancel) + Topic 2개(feedback/status)를 묶어 만든 것 | 에피소드 구조와 거의 같다. 목표=시작, 피드백=매 스텝, 결과=종료, 취소=조기종료 |

> Service를 동기식으로(응답을 기다리며 블로킹) 호출하면 안 되는 경우가 있다.
> 단일 스레드 executor에서 콜백 안에 동기 호출을 넣으면 응답을 처리할 스레드가
> 남아있지 않아 그대로 멈춘다. 아래 Executor 항목과 같은 원인이다.

## 구조

| 개념 | 설명 | 이해에 쓴 비유 |
|---|---|---|
| Node | 역할 하나만 맡는 실행 단위. 프로세스와 1:1이 아니다 — 여러 노드를 한 프로세스에 올릴 수 있고(composition), 그러면 노드 간 데이터 복사를 줄일 수 있다 | 프로젝트별로 환경을 분리하는 것과 같은 "격리"의 사상 |
| Package / Workspace | Package = Node·메시지·launch를 묶은 배포 단위. 사람이 아니라 그들을 담는 부서 폴더에 가깝다. Workspace = 여러 Package를 모은 작업 폴더 | 로컬 패키지를 editable로 설치하는 것과 같은 개념. colcon build가 그 설치 과정을 대신한다 |

통신은 Package 경계와 무관하다. 서로 다른 패키지의 노드끼리도 같은 토픽으로 통신한다.

## 설정과 실행

| 개념 | 설명 | 이해에 쓴 비유 |
|---|---|---|
| Parameter | 노드 시작 시 또는 실행 중에 바꿀 수 있는 설정값. 노드마다 따로 갖는다 — 전역 파라미터 서버 같은 건 없다 | 학습률·환경 수를 config로 빼서 주입하는 것과 같은 사상 |
| Launch file | 여러 패키지에 흩어진 노드들을 파라미터까지 포함해 한 번에 실행하는 스크립트. Python·XML·YAML로 쓸 수 있다 | 여러 작업을 한 스크립트로 동시에 띄우는 것과 같은 개념 |

## 로봇을 표현하는 것들

| 개념 | 설명 | 이해에 쓴 비유 |
|---|---|---|
| URDF | 로봇의 링크(뼈대)·조인트(관절)를 XML로 적은 설계도. 반복되는 부분은 보통 xacro 매크로로 줄여 쓴다 | MJCF와 같은 역할. 물리 파라미터 표현은 MJCF보다 얕다. MuJoCo는 URDF를 직접 읽을 수 있고, Isaac Sim도 URDF/MJCF Importer를 둘 다 제공한다 |
| TF2 | 여러 좌표 프레임(map/odom/base_link/센서 프레임) 사이 관계를 트리로 관리하고, 최근 기록을 버퍼에 담아 특정 시각의 값도 조회할 수 있게 한다 | forward kinematics와 같은 문제를 "시간표가 딸린, 되감기 가능한 버전"으로 여러 프로세스에 걸쳐 처리하는 것 |
| RViz2 | Topic과 TF로 들어오는 데이터를 3D로 그려주기만 하는 시각화 도구. 물리 계산은 전혀 하지 않는다 | 물리 엔진과 완전히 분리된 별도 프로그램. 데이터가 실물에서 왔는지 시뮬에서 왔는지 몰라도 된다 |

TF 트리에는 두 가지 제약이 있다. 각 프레임의 부모는 정확히 하나여야 하고, 트리 전체는 하나의 루트로 연결돼야 한다. 두 노드가 같은 프레임을 동시에 발행하면 값이 튄다. 그리고 변하지 않는 관계(센서 장착 위치 등)는 /tf가 아니라 /tf_static으로 보낸다.

## 네트워크

| 개념 | 설명 | 이해에 쓴 비유 |
|---|---|---|
| DDS / ROS_DOMAIN_ID | 노드들이 서로를 찾는 실제 통신 계층(DDS)과, 같은 네트워크 안에서 그룹을 나누는 번호 | 프로세스별로 자원을 격리하는 네임스페이스 개념 |
| Namespace | 완전 격리 대신 토픽 이름 앞에 접두어(/robot1/)를 붙여 겹치지 않게 하는 방법 | Domain ID(완전 격리)보다 느슨하게, 감독 노드 하나가 여럿을 동시에 보게 하고 싶을 때 |

ROS_DOMAIN_ID는 보안 기능이 아니다. 같은 도메인에 들어온 노드는 모든 토픽을 읽고 쓸 수 있다. 인증·암호화가 필요하면 SROS2를 따로 써야 한다.

## 계획과 이동 — Nav2 생태계

| 개념 | 설명 | 이해에 쓴 비유 |
|---|---|---|
| Nav2 | 지도 앱과 오토파일럿을 합친 ROS 2 공식 내비게이션 스택 | — |
| AMCL | 이미 있는 지도 위에서 파티클 필터로 위치를 추정해 map→odom을 보정 | 눈 감고 걷다가 벽을 더듬을 때마다 위치 감각을 재보정하는 것 |
| Costmap | 장애물 근처를 "비싼 길"로 만들어 자연스럽게 피해가게 하는 지도 레이어 | 지도 앱의 실시간 교통 히트맵 |
| 전역 Planner (navfn/smac) | planner_server 노드 안에서 전체 경로를 한 번에 계산하는 플러그인 | 목적지를 찍었을 때 뜨는 전체 경로선 |
| 지역 Controller (dwb/mppi) | controller_server 노드 안에서 매 순간 실시간 회피를 계산하는 플러그인 | 오토파일럿을 켜놔도 갑자기 반응해야 하는 순간 담당 |
| BT Navigator | Behavior Tree로 전체 순서(계획 → 따라가기 → 복구)를 지휘하는 노드 | 목표 수신·경로 계산 호출·따라가기 호출이 전부 Action으로 이뤄진다. Action 개념이 그대로 재사용된다 |

## 제어와 위치 추정

| 개념 | 설명 | 이해에 쓴 비유 |
|---|---|---|
| ros2_control | 정해진 주기로 센서 읽기(read) → 계산(update) → 모터 명령(write)을 반복하는 실행 레이어. controller_manager가 주기를 돌리고, 하드웨어별 코드는 hardware_interface 플러그인 안에 들어간다 | 서보 제어 스크립트의 콜백 구조를 표준화한 버전. 벤더 SDK 호출 코드가 플러그인 안으로 들어간다 |
| robot_localization | 휠 오도메트리와 IMU를 칼만 필터로 섞어 odom→base_link를 부드럽게 추정한다. 지도는 모른다 | AMCL과 짝을 이뤄 TF 트리의 두 화살표를 각각 담당 — map→odom은 AMCL, odom→base_link는 이것 |
| MoveIt2 | 팔의 경로 계획·충돌 회피·역기구학 담당. 계획만 하고 실행은 ros2_control이 맡는다 | URDF·TF2·Action을 그대로 갖다 쓰는 패키지. Nav2의 매니퓰레이터 버전 |

ros2_control이 표방하는 주기는 설정값(update_rate)이고, 그 주기를 실제로 지키는 것은 별개 문제다. 일반 리눅스 커널에서는 지터가 생기고, 엄격한 주기가 필요하면 RT 커널이 필요하다.

## 시스템 관리

| 개념 | 설명 | 이해에 쓴 비유 |
|---|---|---|
| Executor / Callback group | 노드 안 콜백들을 어떤 순서와 동시성으로 처리할지 관리한다. 잘못 두면 데드락이 생긴다 | 웨이터 한 명이 자기 주문을 처리하다 주방까지 직접 가야 하면 그대로 멈추는 것 |
| Diagnostics | 각 노드의 상태(정상/경고/에러)를 표준 형식으로 모아 보여주는 체계 | 자동차 계기판의 체크엔진등처럼 여러 센서를 하나로 집약 |

## 정리하면서 바로잡은 오해

| 처음 이해한 것 | 실제 |
|---|---|
| Package를 "역할이 주어진 팀원"으로 이해 | Package는 사람(Node)이 아니라 그들과 도구를 담는 부서 폴더 쪽. 통신은 Package 경계와 무관하다 |
| Launch file이 한 패키지 안의 노드에 한정된다고 이해 | 서로 다른 여러 패키지의 노드를 launch 파일 하나로 함께 실행하는 경우가 더 흔하다 |
| TF2가 기준 하나만 갖고 시간에 따른 변화를 기억한다고 이해 | 기준(프레임)이 여러 개이고, 그 사이 관계를 트리로 관리하면서 최근 기록을 버퍼링한다 |
| MoveIt2가 로봇의 움직임을 제어한다고 이해 | MoveIt2는 계획만 담당한다. 매 순간의 모터 명령은 ros2_control 몫이다 |
| Node = 프로세스라고 이해 | 여러 노드를 한 프로세스에 올릴 수 있다(composition) |
| Service 호출은 응답이 올 때까지 기다린다고 이해 | ROS 2에서는 비동기 호출이 기본이다. 동기 호출은 executor 구성에 따라 데드락을 만든다 |
